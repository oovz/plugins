# Evidence and research

Use external research only when it can change a factual answer, design, implementation, support decision, or validation, or when the user explicitly requests it.

Match evidence to the claim:

1. use applicable repository instructions, code, tests, manifests, lockfiles, installed versions, reproducible runtime behavior, and history for the current project;
2. use version-matched official documentation, release notes, specifications, and maintainer source for supported APIs and contracts;
3. use maintainer issues and discussions for undocumented behavior and known defects;
4. use credible community sources for operational practice, pitfalls, and alternatives, corroborating consequential claims.

Official documentation establishes a supported contract but may not prove the local installation. Repository and reproducible runtime evidence establish the current system. Community material is advisory: use it to form hypotheses and verify consequential hypotheses before relying on them.

Mark observation, inference, and unknowns. Cite the version and source when an external claim affects a decision.

Stop when the exact answer or change can be named with sufficient confidence. When material evidence conflicts, run the smallest focused follow-up needed to resolve the decision and stop when further search is unlikely to change it. Search again only if validation fails or new evidence exposes a material unknown. Do not research general best practices after the accepted design and repository evidence are sufficient.
